# 設計の考え方と拡張方針

## 1. なぜこの分け方なのか

雑誌制作で壊れやすいのは「1ページを直したら別のページが崩れる」ことと、「号を変えるたびにコードを触る」ことの2つです。この2つを構造で防ぐために、誌面を3層に分けています。

| 層 | 実体 | 誰が触るか | 号を変えると |
|---|---|---|---|
| **設定** | `src/config/magazine.config.ts` | アートディレクター | ほぼ変えない |
| **テンプレート** | `src/templates/*.tsx` + `src/components/magazine/*` | エンジニア | 変えない |
| **コンテンツ** | `content/<issue>/**` | 編集者・デザイナー | **ここだけ変える** |

この分離が守られている限り、64ページでも128ページでも、人物が変わっても、同じテンプレート資産を使い回せます。

## 2. ページ番号を持たないという判断

各ページに `pageNumber` を書かせると、1ページ挿入するたびに以降すべてを手で振り直すことになり、必ず事故が起きます。そこで**台割（`issue.json` の `pages` 配列）の順序だけを真実**とし、ページ番号は読み込み時に採番しています（`src/content/resolve.ts`）。

- 並べ替え＝配列の要素を動かす
- 挿入・削除＝要素を足す・消す
- 左右（偶数＝左／奇数＝右）は採番結果から機械的に決まる
- `span: 2` の見開きエントリは「偶数ページ始まり」をバリデーションが強制する

目次だけは例外で、ページ番号を `toc.json` に明示的に書きます。台割から自動流し込みにすると編集意図（「特集は10ページからと書きたい」など）を上書きしてしまうためです。代わりに、存在しないページを指していればバリデーションがエラーにします。

## 3. 見開きの扱い

ページは「仕上がり＋塗り足し」の媒体ボックス（既定 216×286mm）として描かれます。見開き表示では、隣り合う2ページの**ノド側の塗り足しが重複して見える**ため、スロット側で内側の塗り足しを隠し、仕上がり同士が接する正しい見え方にしています（`.mg-spread__slot`）。

見開きにまたがる1枚のページ（`span: 2`）は、媒体ボックスが 426×286mm になります。単ページ表示では、この1枚を左半分・右半分に切り出して見せます（`.mg-page-clip`）。切り出し幅は媒体幅と同じなので、**ノド側にも3mmの塗り足しが自動的に確保**され、そのままページ単位のPDFに出せます。

## 4. データ駆動の粒度

テンプレートごとのデータ仕様は `src/schema/templates.ts` に Zod で定義しています。React に依存しない純粋なスキーマなので、**Node側のバリデータとブラウザ側の両方から同じ定義を読める**のが要点です。「プレビューでは通ったのに `npm run validate` で落ちる」が起きません。

テンプレートを1つ追加するときに触るのは3か所だけです。

1. `src/schema/templates.ts` に Zod スキーマを足す
2. 同ファイルの `templateMeta` に表示名・カテゴリ・許可span・表記義務を足す
3. `src/templates/` にコンポーネントを書き、`registry.tsx` に1行足す

スタイルは `src/styles/templates.css` に `.tpl-<テンプレートID>` 配下で書きます。この名前空間規約が「1ページの修正が他ページに波及しない」ことを担保しています。

## 5. 印刷用とWEB用の分離

- 誌面のスタイル：`magazine.css` / `templates.css`
- ガイド（塗り足し・セーフティ・グリッド）：`guides.css` — 純粋なオーバーレイで、誌面のレイアウトには一切干渉しません
- PDF出力：`print.css` + `src/print/PrintDocument.tsx`
- プレビューアプリのUI：`app.css` — PDFには読み込まれません

プレビューは誌面を mm 実寸で組んだうえで `transform: scale()` だけを掛けています。**画面で見たものと、PDFに出るものが構造的に同じ**になるためです。

## 6. PDF出力の方式

全ページを1つのHTMLに縦に並べ、CSSの `@page` でページサイズを指定し、ブラウザの改ページに任せています。1ページずつ出力して結合する方式に比べて、

- ページ順が構造的に保証される（結合順の事故がない）
- ブラウザの起動が1回で済み、64ページで十数秒
- ページをまたぐリンク・目次構造がそのまま残る

という利点があります。トンボは台紙（`MarkSheet`）を挟むだけで、誌面側は一切変わりません。

## 7. 今後の拡張方針

### 短期（次のフェーズで着手しやすいもの）

- **テンプレートカタログ号**：全46テンプレートを1ページずつ並べた `content/issue-catalog/` を用意すると、デザイナーが選ぶときの見本帳になります。台割を書くだけで作れます。
- **目次の半自動生成**：`toc.json` に `"auto": true` のエントリを許可し、台割から候補を生成して編集者が取捨選択する方式。
- **原稿量のアタリ**：`src/lib/richtext.ts` の `countCharacters` を使い、テンプレートごとの「収まる文字数の目安」を台割パネルに出す。入稿前ではなく**入稿時**に溢れが分かるようになります。
- **差分プレビュー**：号のスナップショットを保存し、修正前後のページを並べて見る。校了作業が速くなります。

### 中期

- **承認ワークフロー**：`PageSpec` に `approval: { state, by, at }` を足し、「未承認ページがあるとPDF出力できない」をバリデーションに追加。`flags.draft` がその原型です。
- **ランキングAPI連携**：`content/<issue>/ranking/*.json` を生成するスクリプトを追加するだけで、テンプレート側は無変更で対応できます。データの形さえ守れば供給元は問いません。
- **QRアクセス計測**：`issue.json` の `qr.trackingBase` に計測ドメインを設定すれば、誌面データを触らずに全QRが計測URL経由になります。ページ単位の効果測定は `trackingParams` に `page` を足す拡張で対応できます。
- **CMYK / PDF-X 変換の自動化**：`scripts/export-pdf.ts` の後段に Ghostscript を挟む。ただし色の最終責任は印刷会社側にあるため、あくまで確認用の位置づけにすべきです。

### 長期

- **複数号の横断管理**：`content/` 直下に号が並ぶ構造はそのままで、号一覧・バックナンバー・人物インデックスを生成できます。
- **入稿パッケージの自動生成**：PDF＋使用画像＋フォントライセンス＋台割表をzipにまとめる。
- **エディタ画面**：現在のプレビューアプリは閲覧専用ですが、台割パネルはドラッグ＆ドロップでの並べ替えに拡張しやすい構造にしてあります（順序＝配列なので、配列を書き戻すだけで済みます）。

### やらないほうがよいこと

- **設定値をテンプレート側に直書きすること。** 判型変更が破綻します。数値は必ず `magazine.config.ts` → CSS変数を経由してください。
- **テンプレートを1ページ専用にすること。** 「P24専用テンプレート」を作り始めると、64ページのベタ書きに逆戻りします。差分はデータ（`surface`、`columns`、`layout` など）で吸収してください。
- **グローバルCSSに `.tpl-` 接頭辞なしのクラスを足すこと。** 他ページへの波及事故の温床になります。
